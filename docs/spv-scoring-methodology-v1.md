# SPV scoring methodology v1 — утверждённая продуктовая основа

## Статус

**DECIDED BASELINE.** Документ фиксирует продуктовую и расчётную основу `SPV-1.0`, согласованную 2026-09-30. Он является источником для последующей implementation-ready specification, схемы данных, API-контрактов, конфигурации методики и Admin workflow.

Это ещё не production-конфигурация и не разрешение начинать реализацию без feature specification, verification criteria и review.

Связанные документы:

- `project-evaluation-criteria.docx` — исходная методика;
- `docs/scoring-methodology-review.md` — аудит исходной методики;
- `docs/scoring-methodology-decisions.md` — история решений и альтернатив;
- `docs/product.md` — продуктовый контекст;
- `docs/architecture.md` — системная архитектура.

## 1. Модель результата

Система разделяет независимые слои:

```text
Questionnaire → A: качество и готовность проекта
Documents     → B: документальная подтверждённость
Risk rules    → Risk Flags / Hard Stops
AI            → извлечение, сопоставление, объяснения, рекомендации
Admin         → проверка, разрешение конфликтов, пересчёт, публикация
```

AI не назначает и не корректирует A или B. Формальные показатели рассчитываются детерминированным кодом по версии методики.

## 2. A — качество и готовность проекта

### Значение

`A` показывает качество и готовность SPV-проекта по методике платформы.

`A` не означает:

- вероятность получения инвестиций;
- вероятность успеха бизнеса;
- кредитный рейтинг;
- инвестиционную рекомендацию;
- факт проведения due diligence.

### Формула

Каждый критерий сначала переводится в `criterion_score` от 0 до 10. Затем рассчитывается его взвешенный вклад:

```text
criterion_contribution = criterion_weight × criterion_score / 10
A = Σ criterion_contribution
```

Диапазон `A`: `0–100`.

### Блоки и веса

| Блок | Критерий | Вес в A |
|---|---|---:|
| Финансы | Собственные средства | 15% |
| Финансы | Подтверждённое софинансирование | 15% |
| Команда | Опыт Project Lead / CEO / Managing Founder | 10% |
| Команда | Команда проекта | 10% |
| Продукт / готовность | Что уже есть | 10% |
| Продукт / готовность | Потенциал масштабирования | 10% |
| Экономика и рынок | Project IRR | 10% |
| Экономика и рынок | Проработка сбыта | 10% |
| Юридическая часть | Долги и судебные риски | 10% |
|  | **Итого** | **100%** |

Критерий «доля инвестора» не входит в A.

### Block scores

Для объяснения результата система дополнительно показывает вклад каждого блока. Block score должен вычисляться из входящих критериев и отображаться отдельно от общего A. Точная UI-шкала block score фиксируется в feature specification без изменения весов A.

## 3. Правила критериев A

### 3.1. Что уже есть

Ресурс считается существующим, если на дату подачи заявки заявитель или участник будущей SPV имеет юридически оформленное право использовать его для проекта.

Учитываются:

- собственность;
- оформленная аренда;
- действующий лизинг;
- лицензированное использование;
- юридически оформленный ресурс партнёра.

Не учитываются:

- будущая покупка после получения инвестиций;
- устная договорённость;
- намерение оформить право позднее.

Тип права сохраняется как минимум в одном из значений:

```text
owned | leased | licensed | partner_owned
```

Исходные веса ресурсов сохраняются. `Только проект, ничего нет` взаимоисключающий с остальными вариантами.

```text
resource_score_raw ∈ [0, 9.5]
resource_score = resource_score_raw / 9.5 × 10
```

Для аудита сохраняются raw и normalized значения.

### 3.2. Собственные средства

| Доля собственных средств | Балл |
|---|---:|
| `<10%` | 2 |
| `10–<20%` | 4 |
| `20–<30%` | 6 |
| `30–<40%` | 8 |
| `40–50%` | 9 |
| `>50%` | 10 |

Наличие средств в критерии ресурсов и процент участия учитываются намеренно: первое характеризует текущую готовность, второе — финансовую вовлечённость основателя.

### 3.3. Софинансирование

| Состояние | Балл |
|---|---:|
| Подтверждённого софинансирования нет | 0 |
| Подтверждённое софинансирование есть | 10 |

Допустимые основания:

- подписанное инвестиционное обязательство;
- кредитное одобрение;
- подтверждённый грант;
- договор финансирования;
- документально подтверждённое финансирование партнёра.

Предварительный интерес без обязательства не считается подтверждением. Сумма софинансирования сохраняется отдельно.

### 3.4. Опыт

Оценивается опыт Project Lead, CEO или Managing Founder, непосредственно ответственного за реализацию проекта. Нельзя автоматически использовать максимальный опыт консультанта или произвольного участника команды.

При нескольких руководителях выбирается наиболее релевантный ключевой руководитель, формально закреплённый за проектом. Опыт остальных участников хранится отдельно.

Исходная шкала пока переводится в следующую непересекающуюся трактовку. **ASSUMED:** точное включение граничных значений должно быть подтверждено в implementation specification, поскольку исходный документ использует пересекающиеся формулировки.

| Опыт ключевого руководителя | Балл |
|---|---:|
| Нет опыта | 0 |
| Больше 0, но меньше 1 года | 3 |
| От 1 до менее 3 лет | 5 |
| От 3 до 5 лет включительно | 8 |
| Свыше 5 лет | 10 |

### 3.5. Команда

Оценка опирается на закрытие функций:

- продукт/технология;
- продажи;
- операционное управление;
- финансы;
- отраслевая экспертиза.

Один человек может закрывать несколько функций. Для максимального балла все критичные для конкретного проекта функции должны быть закреплены за конкретными людьми.

Шкала сохраняет исходные уровни `0/2/4/7/10`; чек-лист используется для объяснимого выбора уровня. AI может предложить уровень, но пользователь подтверждает факты, после чего score engine назначает балл.

### 3.6. Потенциал масштабирования

Для максимального уровня проект объясняет:

- куда планируется масштабирование;
- за счёт чего растёт объём;
- какие дополнительные ресурсы потребуются;
- какие ограничения могут возникнуть.

Шкала:

| Состояние | Балл |
|---|---:|
| Потенциала нет | 0 |
| Потенциал есть, но стратегического плана нет | 5 |
| Есть стратегический план с обязательными элементами | 10 |

AI может предложить категорию, но окончательные факты подтверждаются пользователем.

### 3.7. Project IRR

Используется `Project IRR`, рассчитанный по nominal after-tax unlevered project cash flow.

Включаются:

- первоначальные инвестиции;
- операционные денежные потоки;
- CAPEX;
- изменение working capital;
- налоги;
- residual/terminal value, если она явно предусмотрена.

Не включаются:

- получение кредита;
- погашение кредита;
- проценты по долгу;
- внесение equity инвестором;
- дивиденды.

Минимальный формат:

```text
Year 0, Year 1, ..., Year N
```

- минимум 5 прогнозных лет;
- максимум 10 прогнозных лет;
- Year 0 содержит первоначальные инвестиции;
- terminal value по умолчанию отсутствует;
- при наличии terminal value сохраняются значение и метод расчёта.

IRR рассчитывается детерминированным кодом, а не AI.

Если денежные потоки имеют несколько смен знака, дают несколько IRR или не позволяют определить IRR, создаётся статус:

```text
IRR_REQUIRES_REVIEW
```

AI не выбирает одно из возможных значений.

Шкала баллов пока приводится к следующей непересекающейся трактовке. **ASSUMED:** точные границы, включая обработку отрицательного IRR, должны быть явно подтверждены в implementation specification; исходный документ этого не определяет.

| Project IRR | Балл |
|---|---:|
| `<20%` | 3 |
| `20–<30%` | 5 |
| `30–<40%` | 7 |
| `40–<50%` | 9 |
| `≥50%` | 10 |

Если финансовый модуль исключается из конкретного раннего feature slice, поле временно называется `заявленная годовая доходность проекта`, маркируется как предоставленное заявителем и не выдаётся за рассчитанный IRR.

### 3.8. Проработка сбыта

| Уровень | Балл |
|---|---:|
| Сбыт не проработан | 0 |
| Рынок понятен, конкретных покупателей нет | 2 |
| Конкретные покупатели определены | 4 |
| Есть LOI или предварительные договорённости | 7 |
| Подписанные контракты подтверждают существенную часть планируемых продаж | 10 |

Сохраняются:

```text
contract_value
planned_revenue
coverage_ratio = contract_value / planned_revenue
```

На первой версии coverage ratio может быть информационным показателем и не обязан автоматически менять балл. Период planned revenue должен совпадать с периодом contract value.

Наличие контракта как ресурса и его влияние на сбыт учитываются намеренно: это существующий актив и подтверждение спроса соответственно.

### 3.9. Долги и судебные риски

Данные разделяются минимум на:

1. существенную просроченную задолженность;
2. текущие существенные судебные разбирательства, способные повлиять на проект.

Для каждого риска сохраняются:

- тип;
- субъект;
- сумма, если известна;
- источник;
- verification status;
- комментарий администратора.

Для первой версии исходный балл остаётся бинарным:

- отсутствуют существенная просроченная задолженность и существенные текущие разбирательства → 10;
- присутствует хотя бы один из этих рисков → 0.

Юридические риски дополнительно отражаются отдельными Risk Flags.

## 4. Investment Terms

Условия сделки не входят в A.

Хранятся отдельно:

- требуемая сумма инвестиций;
- предлагаемая доля;
- implied valuation;
- тип сделки.

Удалённый критерий доли инвестора не заменяется искусственным десятым вопросом. Освободившийся финансовый вес распределён между собственными средствами и софинансированием по 15%.

## 5. B — документальная подтверждённость

### Значение

`B` показывает уровень документального подтверждения данных, а не уверенность AI.

### Коэффициенты

| Verification status | Коэффициент |
|---|---:|
| Полностью подтверждено | 1.0 |
| Подтверждено частично | 0.5 |
| Документального подтверждения нет | 0 |
| Документы противоречат заявленному значению | 0 + `conflict flag` |

### Формула

B использует те же веса критериев, что A:

```text
B = Σ criterion_weight × verification_coefficient
```

Диапазон `B`: `0–100`.

B не изменяет A и не перезаписывает ответ пользователя.

Допустимый внутренний показатель:

```text
Adjusted Score = A × B / 100
```

Он используется только в Admin-панели для приоритизации и не является основным публичным рейтингом для инвестора.

Для каждого критерия сохраняются отдельно:

```text
answer_value
document_value
verification_status
source
admin_comment
```

Минимальные действия администратора:

```text
Confirm | Partial | Conflict | No Evidence
```

## 6. Hard Stops

### HS-01 — Нет ответственного исполнителя

Нет конкретного человека, отвечающего за реализацию проекта. Публикация блокируется.

### HS-02 — Не заполнены обязательные данные

Данных недостаточно для корректного расчёта обязательных критериев. A имеет статус preliminary; публикация блокируется.

### HS-03 — Критическое неразрешённое противоречие

Анкета и документ содержат существенно разные значения, а конфликт не разрешён. Публикация блокируется до разрешения.

### HS-04 — Невозможно определить заявителя или владельца проекта

Нельзя установить физическое или юридическое лицо, представляющее проект. Публикация блокируется.

Hard Stop не изменяет A или B.

## 7. Risk Flags

Следующие условия не являются hard stops первой версии:

- отсутствие софинансирования;
- отсутствие подтверждённых контрактов/сбыта;
- низкий IRR;
- задолженность;
- судебные разбирательства;
- слабая команда;
- низкий уровень документального подтверждения.

Минимальные коды:

```text
RISK_NO_CONFIRMED_SALES
RISK_DEBT
RISK_LITIGATION
RISK_NO_COFINANCING
RISK_LOW_IRR
RISK_WEAK_TEAM
RISK_LOW_EVIDENCE
```

Risk Flag показывается отдельно и не изменяет A.

## 8. Обязательные данные и конфликты

- Обязательный пропуск не исключается из знаменателя.
- При обязательных пропусках A является preliminary.
- Публикация preliminary-проекта запрещена.
- AI не заменяет answer value документальным значением.
- Первоначальный ответ, найденное значение и источник сохраняются после разрешения конфликта.
- Администратор может выбрать итоговое значение, оставить комментарий или вернуть проект пользователю.

## 9. Admin MVP

### Список проектов

Показывает:

- название;
- статус;
- A;
- B;
- Risk Flags;
- Hard Stops;
- дату создания.

Статусы:

```text
Draft | Review | Conflict | Ready | Published
```

### Просмотр проекта

Показывает:

- анкету и ответы пользователя;
- criterion scores и block scores;
- A и B;
- документы;
- AI-extracted values и источники;
- Risk Flags и Hard Stops.

### Verification

Для значения показываются:

```text
User Answer
Document Value
Source
Verification Status
Admin Comment
```

### Конфликты

Администратор может:

- выбрать итоговое значение;
- оставить комментарий;
- вернуть проект пользователю;
- не удалять первоначальный ответ и документальное значение.

### Пересчёт

Действие `Recalculate` заново вычисляет:

- criterion scores;
- block scores;
- A;
- B;
- Risk Flags;
- Hard Stops.

Пересчёт выполняется по явно выбранной methodology version и сохраняется в истории.

### Решение

Минимальные действия:

```text
Return for Correction | Approve | Publish
```

При активном Hard Stop действие `Publish` недоступно.

Фактическая аудитория и видимость статуса `Published` определяются отдельной feature specification; investor matching не входит в этот Admin MVP.

### Audit Log

Сохраняются минимум:

- actor;
- timestamp;
- изменённое поле или действие;
- старое значение;
- новое значение;
- причина изменения, решения или пересчёта.

## 10. Версионирование

Первая утверждённая конфигурация имеет идентификатор:

```text
SPV-1.0
```

Любое изменение критериев, весов, формул, нормализации, hard stops или score mapping создаёт новую methodology version.

Каждая оценка хранит минимум:

```text
methodology_version
score_at_submission
current_score
scored_at
recalculated_at
recalculation_reason
```

Историческая оценка не пересчитывается молча.

Предполагаемое расположение versioned configuration:

```text
scoring/spv-v1.json
```

Конкретный формат и путь утверждаются в implementation specification.

## 11. Явные non-goals Admin MVP

- визуальный конструктор методики;
- редактирование весов через UI;
- создание критериев через Admin UI;
- сложный RBAC;
- CRM;
- investor matching;
- BI dashboard;
- автоматический полноценный due diligence;
- управление версиями методики через Admin UI;
- автоматическое инвестиционное решение.

## 12. Пилот и калибровка

На пилоте показываются числовые A и B без категорий `низкая / средняя / высокая`.

После минимум 15–20, предпочтительно 20–30, реальных проектов анализируются:

- распределение A и B;
- экспертная оценка проектов;
- фактический переход на следующий этап;
- полезность Risk Flags;
- ложноположительные и ложноотрицательные результаты.

Только после этого вводятся публичные категории и проходные пороги.
